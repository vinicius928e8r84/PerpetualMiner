# The opener fake lives in the test profile, and the permission is written as Chrome keeps it

The opener is not HTTP: it is a Native Messaging host. The fake (`e2e/fakes/abridor.js`) is registered in the Chromium test profile (`<profile>/NativeMessagingHosts/<host>.json`: with a profile of its own, that is where the Linux Chromium looks for the user's hosts), and Chromium runs it as it would the real one, with the 4-byte length plus JSON message. It answers with the examples of the contract that `complemento/test_abridor.py` checks on the real script.

The warning that asks for the optional `nativeMessaging` permission belongs to Chrome, and Playwright cannot reach its buttons. So the fixture grants the permission by writing it into the profile's preferences as Chrome keeps it after the person presses Permitir (on Mac and Windows the `Secure Preferences` file resets what lacks its signature, so the copy brings `nativeMessaging` in the manifest). Without that option the extension arrives as from the store, without the permission, and the request waits for the warning.

On Windows the Chromium does not look for the host in a profile folder: it reads the manifest path from the user's registry (HKCU\Software\Chromium for the Playwright Chromium; the owner's Chrome uses `Google\Chrome`, which the fake never touches). The key is one per computer, so on Windows only one test with the opener runs at a time (`--workers=1`). And there is no "no opener" the fake can reach there: removing its key makes Chromium fall back to the real opener that the owner's Conexão registered, and the test would open the owner's Anki (it happened). A test that simulates "no opener" is skipped on Windows (`SEM_ABRIDOR_IMPOSSIVEL`).
