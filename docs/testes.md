# Testing

The extension is tested for real in Chromium via Playwright, from `e2e/` (its own `package.json`, so the unpacked root stays free of Node files):

```bash
cd e2e
npm ci           # once
npm run setup    # once: downloads Playwright's Chromium
npm test         # launches Chromium with the unpacked extension and runs the suite
```

On Linux/WSL, Chromium also needs system libraries (NSS, ALSA…): `sudo npx playwright install-deps chromium`, once.

The browser sees only the DejaVu fonts (`e2e/fontconfig/fonts.conf`, set as `FONTCONFIG_FILE` by `e2e/fixtures.js`; Debian/Ubuntu package `fonts-dejavu-core`; the machine's own fontconfig, `50-user.conf` and `51-local.conf`, is left out on purpose), so the host pages' fallback fonts and symbol glyphs are the same on a dev machine and on the CI runner, and the `-linux` visual references hold on both.

- The fixtures (`e2e/fixtures.js`), the fakes (`e2e/fakes/`), the local test pages (`e2e/pages/`), the Veio showcase (`e2e/vitrine/`) and the list of visual references (`tests/*-visual.spec.js`) are described in the `e2e-suite` skill: `.claude/skills/e2e-suite/SKILL.md`. Open it before adding or changing an e2e test.
- `HEADED=1 npm test` shows the browser.
- The computer's port 8766 is out of the test Chromium's reach (#551). Playwright's routing does not see the first navigation of a tab the extension opens with `chrome.tabs.create`, nor the redirect it follows (the ChatGPT login's return to `http://127.0.0.1:8766/auth/callback`); left alone, that request goes to the real port, where an open Anki answers it. So the fixture maps `127.0.0.1:8766` and `localhost:8766` (`--host-resolver-rules`) to the test Conexão's port: the worker fixture `portaDaConexaoDeTeste` (`e2e/fakes/porta-da-conexao.js`), or the real add-on server's port with `PM_CONEXAO=real`. On that port the fake answers the return tab (`fakes.anki.responderNaPortaDeTeste`, the same login state as the routed `/auth/callback`) and drops the connection of anything else, as a closed port would; `fakes.anki.chegaramNaPortaDeTeste` lists what arrived (transport, not stored state). Proved by `e2e/tests/configuracoes-chatgpt.spec.js` › `a aba de retorno do ChatGPT chega à porta da Conexão de teste, nunca à porta 8766 do computador` (in Chromium) and by `testes/test_fake_anki.js` (the port alone, over HTTP). No test listens on 8766: with the port taken, an Anki that opens meanwhile leaves its Conexão down.
- `PM_CONEXAO=real` keeps the fake's failures and requests in front of the real add-on server (`rotaComFalhasNaFrente` in `e2e/conexao-real.js`, which asks `fakes.anki.naFrente`): `desligar`, `silenciar` and `responder` still act and `requisicoes` still counts, and every other request reaches Python. The world the fake was given reaches it too: before a request is forwarded, the real Conexão gets the profile (`abrirPerfil`; `null` is the Anki on the profile screen; `definirPerfis` gives the profile list and the marked one, and after each `/anki/profile*` request `perfilAberto`/`perfilMarcado` mirror the real) and one collection made of the contract's (`abrirColecao`), the Baralhos of `definirBaralhosDoAnki` and, for `definirVocabulario`, one note per word in the Baralho the vocabulary request names, with the cards of its situation; what Python computes from them is what the extension reads. The read failures (`falharVocabulario`, `falharBaralhos`) stay in front, like `desligar`, and so do the Envio's (`recusarEnvios`; `perderARespostaDoEnvio` lets the real create it and drops the answer). An Envio is created in the real queue (its worker stays off), and after each `/jobs` request `fakes.anki.envios` mirrors what the queue keeps (`servir.py` › `envios`), so a test reads the stored request, `keywords` fixed included. `moverEnvio`, `concluirEnvio`, `receberEnvio` and `apagarAsFrases` reach the real queue too (`falharApagarFrases` stays in front), through its gate (`Fila.mudar`, `Fila.criar`, `Fila.apagar_as_frases`; a contract queue, `definirFila`, is seeded as the add-on's tests seed it), before the next request goes on: a move the state machine refuses fails the test, and an Envio the fake concludes from the queue goes through `running` first, as a real one does. The real queue stamps the time of each change, so a test that sets `atualizadoEm` skips in this mode. The key the test keeps only in the Conexão (`guardarChaveNaConexao`, `guardarRemocaoNaConexao`, `esquecerAChave`) is written to the real `chaves/openai.json`, and after each `/ia/openai/*` request `chaveNaConexao`/`estadoDaChave` mirror it; a key that crosses the cloud (`fakes.google`) does not, since the real Conexão has a cloud of its own. The ChatGPT login the test gives (`chatgpt.definir`) is set in the real Conexão against its own fake login server (`situar_o_login`), and after each `/ia/chatgpt/*` request `chatgpt.situacao` mirrors it; a login done through the browser does not run in this mode, because the browser and the real Conexão have different fake login servers. Every forwarded request waits for the world and the queue changes sent before it. `definirBaralho` does not reach it: its numbers are not what a collection gives (`porCartao` is not words ÷ cards). So the specs that only use those controls run against the real server too: the nightly `e2e-conexao-real` job (`.github/workflows/noturna.yml`) lists them, and `.github/workflows/testes.yml` runs a subset of them on the PR. `test.use({ conexaoDesligadaAoAbrir: true })` turns the Conexão off before the extension opens, for a test that must never see a check that started earlier answer `ligada`.
- While working, run only the specs of the area you changed (`npx playwright test <specs> --workers=2`); the whole suite runs in CI (`.github/workflows/testes.yml`, with the Node, engine and add-on tests), not on your machine, but a PR that touches only the add-on, the engine or documentation skips the e2e there (`scripts/ci/selecao-de-testes.js`), so run the e2e specs a cross-read could break yourself. A test that also fails on `main` has an open issue: do not prove it again.
- Tests assert what the person sees and what ends up stored, never internal functions. A test that acts reads the stored state afterwards and compares it with a concrete value (`e2e/estado-final.js`; rule `e2e-estado-final`); the read comes after the last action and reaches an `expect`; a fake's reader of what it kept is declared `@estado-guardado`; one that stores nothing says `// Exceção de teste: sem-estado-guardado — <reason>`. Three narrow exceptions, each named in the test's comment:
  - Where Chromium gives Playwright no way to drive the native UI or clock (the context menu, the toolbar badge, the midnight alarm, an extension update), a test does what Chrome would do — calls the function Chrome would call (`minerarSelecaoDoMenu`, `registrarMenuDeContexto`, `aoInstalar({ reason: 'update' })`) or fires the alarm early under its own name — and asserts what gets stored or what is handed to Chrome (`chrome.action.getBadgeText`, `getTitle`, the next alarm's time).
  - Until a surface shows a catalog state, the catalog's own guarantees (every ID present, pt-BR numbers) are asserted through `PerpetualMiner.textoDaVoz`, inside an extension page. These move to the screen when the surface is rebuilt.
  - Two guarantees of the base components have no on-screen trigger of their own, so the test calls the component's own function and still asserts the visible result: how long a toast of a given length *stays on screen* (`mostrarToastDeSucesso`), and that a phrase carrying markup is written as text (`escreverFrase`). The surfaces that call them assert the same thing through the screen once they are rebuilt.

The add-on's contract with the extension is tested from both sides on the same examples: `complemento/test_servidor.py` (the real server over an in-memory collection) and `e2e/tests/contrato-da-conexao.spec.js` (the fake, which answers from `complemento/contrato/exemplos.json`; a context such as `fakes.anki.abrirColecao(nome)`, `abrirPerfil(perfil)` or `definirItemDeLogin(situacao)` needs an example, which `node testes/test_fake_anki.js` checks).

The Firestore rules are in the repository as `docs/seguranca/firestore.rules`, a copy of what the Firebase console had published on 27/11/2026 (the ranking block is also kept, alone, in `docs/seguranca/ranking-do-grupo.rules`, and the test compares the two). `node scripts/testar.mjs firestore` (heavy group, needs Java 11+; `PM_JAVA` points to it) loads the file in the Firestore emulator and checks the own UID, another UID and no login on `usuarios/{uid}/frases`, `segredos/openai`, `meta/deleted` and `ranking` (`testes/firestore/`). It proves the file, not what is deployed: the repository never publishes rules, so a change to the file still has to be copied to the console by the owner and proved against the real Firebase (#883).

The legacy tests keep running: `node testes/test_sync.js` (loads `lib/sincronizacao.js` for real, two computers over a memory cloud, plus the HTTP adapter over a fake `fetch`), `node testes/test_auto_keyword.js`.

**Every test runs in the gate.** The groups of `scripts/testes.json` are the one list of what runs: a workflow job only calls `node scripts/testar.mjs <group>`. `node scripts/regras/verificar.js` (rule `testes-no-portao`) fails on a test file no group runs, a group no PR workflow calls, and a workflow that runs a test by hand. A `.sh` file of a `node` group runs with `bash` (the `ferramentas` group runs `.agents/skills/verify-perpetualminer/scripts/test_helpers.sh` this way).


## Testing on devices and the Chrome Web Store

- `lib/auto-recarregar.js` (started by `background.js`): only when `chrome.management.getSelf()` says `installType === "development"`, a 1-minute alarm hashes the files `PerpetualMiner.arquivosDaExtensao` lists and calls `chrome.runtime.reload()` when they change (confirmed after 4 s, so a half-finished `git pull` never reloads). Store installs do nothing. Test: `e2e/tests/atualizacao-automatica.spec.js`, on a temp copy of the extension.
- `scripts/atualizar-extensao.sh` (+ `scripts/com.perpetualminer.atualizar.plist.exemplo`) keeps a clone on `main` up to date with `git pull --ff-only`; the header of the `.plist` example says how to schedule it on the Mac.
- `node scripts/empacotar-extensao.mjs` writes `dist/perpetualminer-<version>.zip` (runtime files only, manifest validated; `node testes/test_empacotar.js` checks it); `docs/loja/permissoes.md` holds the permission texts the store asks for, and that test checks them against `manifest.json`.

**Time ceiling.** The Noturna (`.github/workflows/noturna.yml`) sets `PM_TETO_S` on each e2e slice (420 s) and on the add-on (360 s): `testar.mjs` then fails a green run that took longer, with `::error title=Teto de tempo::`, so a slice or the add-on that drifts slower opens the `noturna` issue instead of lengthening every PR wait. The add-on group runs in 2 processes (`"paralelo"` in `scripts/testes.json`, `scripts/unittest-em-paralelo.js`), 4 in the PR CI (`PM_PARALELO=4` in `.github/workflows/testes.yml`); the `node` and `ferramentas` groups run 4 files at a time (`scripts/arquivos-em-paralelo.js`); `PM_PARALELO=1`, or arguments after `--`, run a group in series. The PR CI runs each e2e slice with 2 Playwright workers, and `scripts/ci/fatias-e2e.json` is measured there (`node scripts/ci/fatias-e2e.js --medir` on the 8 slice logs of one PR run): two Chromiums on the runner slow a spec of many short tests more than a spec of long ones, so durations taken with 1 worker leave one slice much longer than another. More workers per slice needs ten green runs in a row first (the owner's rule; https://github.com/vinicius928e8r84/PerpetualMiner/pull/651 has the measurements). The Noturna keeps 1 worker, so its 420 s ceiling still measures the suite on an unloaded runner.
